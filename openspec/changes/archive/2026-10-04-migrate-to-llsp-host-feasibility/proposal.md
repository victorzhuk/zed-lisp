# Proposal

## Why

The parent change `migrate-to-llsp` settles one question by evidence instead of by assumption, and it settles it first: can the WASM extension host compute SHA-256 over a real multi-megabyte release archive *before* any of its contents are trusted, and then extract the published archive layout safely? `zed_extension_api` exposes `download_file` with built-in download-and-extract support, and exposes no hashing helper at all. Until the route is measured, the resolution chain's third step — checksum-verified release download — is unproven, and every design decision downstream of it, including the atomic cutover, rests on it.

Two further questions are already answered nowhere and are cheap to answer, and both are the kind that get quietly turned into contract if they are not written down as research:

- While the language-ID retention gate is open, does a user-supplied `files.associations` entry keep a `.lisp` buffer's dialect across a settings change? The parent's design already states the answer must be treated as an optional user mitigation and never as a substitute for the gate. This child produces the observation that makes that statement evidence rather than intent.
- Does llsp accept a project-file initialization option at all? The example settings in three example workspaces currently configure `lsp.lispico.initialization_options.project_file`. The parent's design keeps that option only as a reviewed migration gate pending verification against the server's real configuration surface.

## What Changes

- One bounded probe runs against an actual published release archive: raw download → SHA-256 over the whole archive compared against the published `SHA256SUMS` entry → safe extraction of the published member layout. The probe records the API surface it used (`download_file` with `DownloadedFileType`, or the absence of any hashing helper), the route it tried, and either the viable route or the failure mode. Everything it writes outside its scratch area is discarded afterward.
- The probe's answer is recorded in `feasibility.md` beside this change, with the archive, the expected digest, the observed digest and the extraction result named. No capability is added on the strength of it, and no crate is added to `Cargo.toml` — a dependency the probe settles on goes through the repository's normal reviewed approval on its own.
- A negative probe result returns the parent design for approval. The digest requirement is not weakened to best-effort, and the cutover does not proceed on a weaker step.
- One research-only observation is recorded: whether a user-supplied `files.associations` entry preserves a `.lisp` buffer's dialect across a settings change while the language-ID gate is open. It is recorded as an optional user mitigation. It is not a shipped setting, not an extension requirement, not documented as required, and not a substitute for the gate.
- One research-only answer is recorded: what llsp's real configuration surface accepts for project-file initialization. The example settings in `examples/go-lispico`, `examples/yagel` and `examples/zhk` follow from it: if llsp does not accept the option, `lsp.lispico.initialization_options.project_file` is removed from those three files and the three shipped schema resources are marked a reviewed migration gate pending an upstream decision. No unsupported option is filtered out of the outgoing request either way.
- **The three schema resources are owned here, as metadata-only edits.** When the measured server does not support the portable context surface, `schemas/lispico-project.schema.json`, `schemas/lispico-catalog.schema.json` and `schemas/lispico-packs.schema.json` are annotated in place: a top-level `$comment` in all three, and — in the project schema only — the `description` sentence that recommends the server's `project_file` initialization option replaced with text that states support is a reviewed migration gate and recommends no initialization option without verified server support. Schema validation semantics, `$id`, titles, schema versions, properties, required fields and references are unchanged. The annotation marks unsupported consumption; it never abandons the required project contract, and it approves no reduced host-aware semantics.
- The cutover, not this child, renames the `lsp.lispico` server entry when it lands its own atomic change. These documents do not treat `lsp.llsp` as an existing entry.

## What does not change

- No capability is added, modified or removed. `llsp-language-server-integration` and `common-lisp-language-server-integration` are authored by the open parent `migrate-to-llsp`, which is the sole normative delta carrier; this child writes no spec delta, because it changes no requirement's contract.
- Schema validation semantics are unchanged. Every validation keyword, `$id`, title, schema version, property, required field and reference in the three annotated schemas keeps its current meaning, and the marking is a review annotation, not a contract relaxation.
- No `extension.toml`, no server entry, no identifier map, no resolution code and no test land here. The cutover is the cutover child's single atomic change.
- The language-ID retention gate is not re-measured here and not claimed here. The baseline child re-derives it against the pinned release; this child only records what a user-level mitigation does while it is open.
- The host-aware parity gap and the upstream analysis gap are not enumerated here. They belong to the baseline record.
- No file outside this change's directory, the three example settings files and the three named schema resources is written. In particular `schemas/**` beyond `lispico-project.schema.json`, `lispico-catalog.schema.json` and `lispico-packs.schema.json` is not in scope, and the documentation child's own prohibition on its schema edits is unaffected.

## Impact

- **This change:** `openspec/drafts/migrate-to-llsp/changes/migrate-to-llsp-host-feasibility/`; plus the `lsp` initialization-option block in `examples/go-lispico/.zed/settings.json`, `examples/yagel/.zed/settings.json` and `examples/zhk/.zed/settings.json` if the configuration-surface answer requires it; plus metadata-only annotations in `schemas/lispico-project.schema.json`, `schemas/lispico-catalog.schema.json` and `schemas/lispico-packs.schema.json` if the option is unsupported. Shared ordering: these settings and schema edits land before `migrate-to-llsp-cutover` retargets the settings and lands the renamed server entry.
- **Downstream:** `migrate-to-llsp-cutover` implements the digest-before-extraction route this probe settles on, and does not proceed if the answer is negative and the design has not been re-approved. It does not undo this child's reviewed schema metadata when it rolls back. `migrate-to-llsp-docs-release` documents the same supported platforms, resolution chain and configuration surface this probe exercised, so the README and the outgoing request cannot disagree.
- **Gate authority:** G4's current result and dependency-approval state are authoritative in this change's `feasibility.md`, bound to the active release facts and the measured host route. No gate state is written into the baseline record; that record holds attributed immutable measurements and an index of gate owners.
- **Dependency:** this change consumes the pinned release, asset names, `SHA256SUMS` entry and archive member layout the baseline child verifies. It does not restate them; if the baseline record moves, the probe re-runs against the record, not against this change's text. A changed active pin invalidates incompatible findings and requires a superseding compatible answer here.

Implementation is not approved by this document. The probe, the two observations, the settings edit and the schema marking are the whole extent of the work; the extension cutover requires separate authorization admitting an atomic unreleased development state, with release held until G1–G5 are met on compatible evidence.

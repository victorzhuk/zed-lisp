# Proposal

## Why

The parent change `migrate-to-llsp` gates its cutover on five named conditions and states them as findings measured on **llsp `v0.2.0` (`88e3e72`)**. That measurement is no longer the state of the world: **llsp `v0.2.1` (`436bc84`)** was published 2026-09-30 and carries a fix, plus a regression test, for the one defect the parent recorded as blocking — `Document` now carries the client-reported `language_id` across a reload, and `reload_documents` passes it back into `Settings::detect`, which is exactly the step the parent found dropped.

That produces a worse failure mode than a stale gate. A gate row inherited from a superseded release reads as evidence while being a measurement of code that no longer ships. The cutover, the documentation and the release note all draw from these rows, so an inherited row propagates a claim nobody re-made.

The split separates measurement from implementation for this reason: the parent's own Authorization section requires separate authorization for every change to the extension, and a child that both measured and cut over would collapse the two. This child is the record only. It re-derives every gate row against the release this split pins, names the release and commit each row was measured on, and leaves the gate states — including the ones it cannot clear — visible.

## What Changes

- One upstream gate record, `gates.md`, in a location both this change and the parent change point at, stating exactly what upstream must guarantee: a settings-driven re-detect preserves each open document's client-reported language ID. No llsp code is patched from this repository; the record is a statement of what the other repository owes, not a diff applied here.
- `gates.md` is the authoritative current record for **G1 and G3 only**. G2 is authoritative in `migrate-to-llsp-cutover/design.md` under Identifier-map evidence, G4 in `migrate-to-llsp-host-feasibility/feasibility.md` under Gate consequence, and G5 in `migrate-to-llsp-acceptance/acceptance.md` under Real-server proof status. This record carries attributed baseline measurements plus an index to those owners; no child keeps a second mutable copy of another child's gate state, and the later measurements append superseding attributed sections rather than rewriting historical facts.
- The language-ID retention behavior is **measured fresh against the pinned release** rather than inherited, and the observation is recorded as observed rather than predicted. A `lispico-cl` `.lisp` buffer opened with `languageId=lispico-cl` is driven through: reader-invalid diagnostics at `didOpen`, one accepted `workspace/didChangeConfiguration`, a second change, an ordinary edit, and a `default_dialect` restore, each recorded separately. The measurement is a live run against the installed binary with the release and commit recorded; a reading of the server's source is not a substitute, and a quote of the parent's `v0.2.0` result is not evidence at all. **No outcome is prescribed**: retention, loss, or recovery is recorded as observed, and G1 is decided afterwards from the retention requirement. The ordinary edit preserves the reader-invalid condition, so a genuine syntax repair can never be recorded as diagnostic loss.
- The historical failure and the current measurement are kept distinct. The `v0.2.0` (`88e3e72`) disappearance of the client-reported identifier and its non-recovery are preserved as attributed history — real measurements of code that this release replaces — and are never a state any current row may inherit. A current run that retains the identifier does not rewrite that history, and a current run that loses it does not make the historical row current again.
- The control dialects are recorded in the same run, whether they pass or fail. Without them a `lispico-cl` buffer that never had the dialect would look identical to one that lost it; missing controls make the measurement incomplete, while a control flip is recorded as observed and leaves G1 unmet rather than making the measurement incomplete.
- The identifier map item is recorded as a **zed-lisp fix, not an upstream gate**: the identifiers llsp declares for all three dialects are read from the dialect files, the shape Zed derives from a display name when no map is declared is read from the editor source, and which of the three modes fail to match without an explicit map is recorded — including the outcome if the derivation happens to coincide for all three. The parent asserts the map is required; this record states what the derivation actually produces rather than restating the assertion.
- The host-aware parity gap is enumerated against the parent's own requirements, with the owning llsp-side change named and the currently open work identified as open **migration** tasks, immutable archived task evidence, and unsatisfied canonical requirements — the three are distinguished, and none is presented as an editable open task that this record may close. No catalog, host-profile, layer or phase behavior is implemented here.
- The release contract is re-verified from the pinned release's published assets and `SHA256SUMS`: the platform matrix, the archive member layout, digest coverage, and every platform with no archive. The unsupported set is listed from the assets, not from the parent's table.
- The upstream analysis gap is recorded on the pinned release as blocking host-context parity, with the three missing lints named: no lint exists for missing libraries, for catalog identity, or for phase violations, and `unresolved_call` defaults to off. The record states that this is not an approved reduction and not parity with the parent's planned checker, and that a later closure requires attributed external completion plus compatible verification of the original requirements.
- External completion and superseding measurement are owned here. This child records the actual identity of the separate llsp-side change that owes host-aware behavior, the evidence that its work completed, the released tag/commit adopted, and the artifact provenance behind it; an unidentified owner or an unreleased promise does not clear G3. On completion it appends a superseding baseline measurement, preserves the `v0.2.1` findings, and re-runs G1, the identifiers, the release assets, digests and layout, the supported platforms, the configuration surface and the complete G3 requirement mapping against the new pin.
- The parent change's gate table and gate section are pointed at the authoritative record for each gate, and this change is pointed at from the parent's task section, so no document can drift into being the sole source of a gate state.
- Implementation admission and release admission are distinguished. G1 and G4 met, the declared identifiers and release contract verified, and a separately recorded authorization permitting an atomic unreleased development cutover are what admit implementation; G2 is then established by the cutover's own map and packaging/dispatch evidence, and G5 by complete acceptance. G3 is unmet on `v0.2.1` and blocks release, not separately authorized unreleased implementation. No release tag, marketplace publication, release package publication or release-readiness claim is permitted until G1–G5 are met on compatible evidence.

## Capabilities

No capability deltas. The requirements this record serves — `Dialect identity is stable for the life of a buffer`, `Host-aware release gates`, and `Explicit language identifier map for the shared server` — are `ADDED` requirements of the parent change's `llsp-language-server-integration` delta, and the open parent `migrate-to-llsp` is their sole normative delta carrier. They are not restated here. A `MODIFIED` delta is also wrong: no requirement's normative text changes because a measurement was re-run, and re-adding a header the parent already adds would collide at archive. This child writes no `specs/` directory and no empty spec file.

## Impact

- `openspec/changes/migrate-to-llsp-upstream-gates/`: this proposal, `design.md`, `tasks.md`, and the record `gates.md`.
- `openspec/changes/migrate-to-llsp/design.md`: the gate table gains pointers to the authoritative record for each gate; "Gates before cutover" distinguishes implementation admission from release admission; "Authorization" names the separate authorization that admits an atomic unreleased cutover while G3 and G5 are open; decision 6 records that the parent is the sole delta carrier and that archive ordering is by change, not by capability name. The `v0.2.0` findings gain the pinned-release measurement. Those edits require approval and are specified by this child's tasks; they do not land with this draft.
- Not touched: `extension.toml`, `src/`, `examples/`, `Cargo.toml`, `README.md`, `CHANGELOG.md`, and anything under `openspec/specs/`. No dependency, no code, no setting.

Downstream reads this record rather than restating it: the feasibility child consumes the release, asset names, `SHA256SUMS` entry and archive member layout verified here and writes G4 only in its own authoritative record; the cutover child builds its identifier map from the declared identifiers verified here, records G2 in its own design and lands only under a separately recorded unreleased authorization; the acceptance child binds its runs to the release pinned here and reports G5 in its own acceptance record; the documentation child states the supported platforms and currently open gate-backed limitations from the authoritative records. None of them re-derives a measurement, and none of them clears a gate by copying prose.

# Proposal

## Why

The extension still registers two independent language servers for the three modes it owns: `[language_servers.sextant]` for `Common Lisp` and `[language_servers.lispico]` for `Lispico Clojure` and `Lispico CL` (`extension.toml:18-24`). The two are served by separate code paths in `src/common_lisp.rs` with separate resolution chains, separate cache layouts, and separate tests, and neither is the server the dialects are actually written for.

The `sextant` path in `src/common_lisp.rs` resolves a configured path, then `worktree.which("sextant")`, then a GitHub release asset restricted to three targets (Linux x86_64/aarch64, macOS aarch64), then a Roswell source build via `ros install victorzhuk/sextant`, with no digest check on the downloaded asset and a cache heuristic that accepts any `sextant-<version>` directory containing an executable file. The `lispico` path resolves a configured path, then `worktree.which("lispico-lsp")`, and otherwise returns an error: its binary has no release at all, and the three shipped example templates point at it.

The shared server for all three dialects is llsp. It is the server whose dialects these modes are, and it publishes verified release archives with a `SHA256SUMS` file — none of which the current download path uses.

Two things this change must not do: ship a partial cutover, and claim a gate it does not own. The upstream gate records and the host-feasibility answer are separate children; this change consumes their results and clears nothing itself.

## What Changes

- Register exactly one language server, `[language_servers.llsp]`, for `Common Lisp`, `Lispico Clojure` and `Lispico CL`, with `[language_servers.llsp.language_ids]` mapping `Common Lisp` → `lisp`, `Lispico Clojure` → `lispico-clojure`, `Lispico CL` → `lispico-cl`. The map is explicit because the server matches only the exact identifiers each dialect declares, and a value derived from a display name coincides with one by accident of normalization rather than by construction.
- Remove `[language_servers.sextant]` and `[language_servers.lispico]`, their dispatch arms, their resolution functions, the sextant download and cache code, the sextant-only `label_for_completion` branch, and the tests over them — in the same change as the registration. No shim, alias entry, fallback, parallel registration or reopen-on-settings-change trick.
- Replace both resolution chains with one: configured binary, then `worktree.which("llsp")`, then a checksum-verified release download. The download verifies the archive against the release's `SHA256SUMS` entry before anything is extracted, stores the binary under a version-named cache directory, records completion only after the digest check, extraction and executable bit all succeed, prunes stale version directories, and reuses a complete verified entry with no network access. A cache miss is not a stopping condition by itself: with an empty cache and a reachable release, resolution reaches verified download and a first installation succeeds. No Roswell, no source build, no installer script, and no archive for a different platform.
- Forward user arguments, environment, initialization options and workspace settings unchanged on all four paths, and surface a configuration the server rejects instead of filtering it out.
- Add behavior contract tests over the real code path for resolution precedence, forwarding per path, digest mismatch, extraction failure, interrupted download state, non-executable cache entry, pruning, offline reuse with and without a usable entry, online first installation with an empty cache, unsupported platform, and unknown server ID.
- Enforce the registration invariants mechanically: `scripts/check_package.py` fails when a registered language has no explicit identifier and when any language server entry other than `llsp` survives; the extension's own dispatch rejects the previous server IDs.
- Retarget the three shipped example templates to the `llsp` entry, preserving every display name, opt-in suffix semantic, snippet and grammar, and carry the recorded `files.associations` observation into `examples/README.md` as an optional user mitigation only while the language-ID gate is currently open.
- Audit the archived predecessor `add-lispico-development-support` against the current canonical Lispico capabilities and author any still-needed normative amendments as deltas in the open `migrate-to-llsp` parent. The archived change and its completion marks are immutable history; the canonical specs are the baseline that already carries shared routing and launch ownership (`lispico-language-server/spec.md:8-28`) and llsp batch ownership plus unmet host-aware parity (`lispico-static-diagnostics/spec.md`, "Shared editor and batch results"). Where the canonical wording is already correct, the amendment map records "already satisfied" and no redundant delta is written. Server identities, the merged launch requirement, the contradictory no-download/Roswell wording and analyzer/checker ownership are each audited; no semantic, context, catalog, library, phase, project-format, source-evidence or data-ownership requirement is reduced and no completion mark moves.

## Capabilities

No child-owned capability delta. The open parent `migrate-to-llsp` is the sole delta carrier for `llsp-language-server-integration`, `common-lisp-language-server-integration`, and any audited canonical predecessor amendment. This child implements those contracts and authors the required parent amendments; its evidence and tasks introduce no competing `MODIFIED` requirement bodies.

This change does not: clear any upstream gate, add or implement host catalog, host-profile, layer or phase behavior, decide the `.lispico.json` initialization-option question (the feasibility child records it; the outgoing request is never filtered regardless of the answer), add host-aware analysis, patch llsp, touch the three `.lispico.json` schema resources (the feasibility child owns their reviewed metadata marking, and cutover does not change or roll back that work), or touch `README.md` and `CHANGELOG.md` (the documentation child owns them against this change's landed state).

## Authorization

Implementation requires a separately recorded authorization permitting an atomic unreleased development cutover, a current passing G1 measurement, verified dialect identifiers and release contract, and G4 met with required dependency approval. G2 is established by the cutover's map and packaging/dispatch evidence. G3 and G5 may remain open during this unreleased state. No release tag, marketplace publication, release package publication, or release-readiness claim is permitted until G1–G5 are met on compatible evidence. If the authorization does not explicitly admit this boundary, implementation remains blocked.
